## 实际流程

1. 访问 `/register`，只填写邮箱并提交申请，不需要邀请码、用户名或密码。
2. 系统保存待审核申请，并向服务器私密配置中的管理员邮箱发送确认通知。
3. 管理员登录“用户管理 → 账号申请审批”，批准或拒绝申请；批准时可设置初始额度。
4. 批准后生成普通账号和随机初始密码，通过邮件发送到申请邮箱。
5. 用户凭邮件中的用户名和初始密码登录，可在个人设置修改密码，修改后初始密码失效。

审批邮件中的链接进入需要登录的管理页面，不通过 GET 或邮件扫描器直接批准。
普通用户不能访问申请审批 API。拒绝或重复提交不会创建额外账号。
发件显示名留空，只显示邮箱地址；真实收件人、发件地址及 SMTP 凭据仅保留在私密环境和受限数据库中。

## 失败恢复

管理员通知与申请人账号邮件分别显示状态。申请记录只保存邮箱和审核状态；初始密码仅在发信时短暂存在，
用户表只保存 bcrypt 哈希，审批响应不返回密码，也不保存明文密码发件队列。

账号邮件失败时，可在首次登录前使用“重试账号邮件”；重试会生成并发送新的初始密码。
已发送成功的邮件不能通过此操作反复重发。中断的发送超过两分钟可重试。
用户首次登录后，该操作不能重置其密码，应使用个人设置或找回密码功能。
重复批准被事务和条件更新拒绝，不重复创建账号或发送凭据。

## 重复邮箱提示（v0.13.2-prlab.5）

用户要求在申请页明确提示已有账号：
- 正式账号已存在：HTTP 409 / registered，页面显示“该邮箱已注册”，并提供登录入口。
- 已有待审批申请：HTTP 409 / pending，页面显示“该邮箱正在审核中”，提醒不要重复提交。
- 新邮箱：保持正常申请流程，HTTP 202。

大小写和首尾空格统一处理，重复提交不新增申请或重复通知。页面使用内嵌提示，避免同时弹出通用网络错误。
已通过模型/控制器/路由/服务回归、前端构建、完整 Go 构建，以及私有数据库副本中的三类实际 HTTP 请求验证。
此次没有更改表结构，发布仅更新 API 平台程序，原有用户与待审批申请保留，失败回滚程序/环境而不覆盖正式数据库。
